## 1. Резюме

MyQRCards MVP — это web-сервис для создания персональной цифровой визитки, доступной по публичной ссылке и QR-коду. Владелец создаёт карточку с контактами и ссылками, а получатель открывает её в браузере без установки приложения, может связаться одним нажатием и сохранить контакт в адресную книгу.

MVP проверяет ключевую гипотезу: пользователи готовы создавать и делиться цифровой визиткой вместо бумажной, а владельцы хотят видеть базовую активность по своей карточке.

## 2. Проблема и ценность

### Проблема
Бумажные визитки легко теряются, их нельзя быстро обновить, а перенос контакта в телефон требует ручного ввода.

### Решение
Пользователь создаёт одну цифровую визитку и делится ею ссылкой или QR-кодом. Получатель открывает страницу, видит актуальные контакты и может сохранить vCard либо перейти в мессенджер.

### Ценность
- Владелец обновляет информацию один раз, без перепечатывания визиток.
- Получатель сохраняет контакт без ручного ввода.
- Владелец видит, что карточку открывали и по каким каналам переходили.
- Продукт можно расширить до корпоративных визиток, NFC и CRM в последующих версиях.

## 3. Целевые пользователи

| Роль | Описание | Основная потребность |
|---|---|---|
| Владелец визитки | Фрилансер, консультант, сотрудник компании, предприниматель | Создать карточку, поделиться ею и получить контакты |
| Получатель визитки | Клиент, партнёр, участник встречи | Быстро увидеть контакты и сохранить их |
| Администратор | Владелец аккаунта | Управлять своими визитками и видеть статистику |

## 4. Scope MVP

### Входит в MVP

- Регистрация и вход по e-mail и паролю.
- Создание одной или нескольких цифровых визиток.
- Редактирование основной информации визитки.
- Публичная страница визитки по постоянной ссылке.
- Генерация и отображение QR-кода.
- Скачивание контакта в формате vCard.
- Кнопки быстрой связи: телефон, e-mail, WhatsApp, Telegram, сайт.
- Базовая статистика: просмотры, клики по каналам, сохранения vCard.
- Удаление и архивирование визитки владельцем.
- Базовая адаптивная вёрстка для мобильных устройств.

### Не входит в MVP

- Нативные приложения для iOS и Android.
- NFC-карты и NFC-теги.
- AI-сканирование бумажных визиток.
- Импорт контактов из телефонной книги.
- Корпоративный кабинет, роли сотрудников и массовое создание визиток.
- Брендирование под компанию и собственный домен.
- Полноценная CRM, сделки, статусы лидов и интеграции.
- Оплата, подписки и тарифные планы.
- Мультиязычный интерфейс, кроме русского и английского.
- Верификация личности и модерация пользовательского контента.

## 5. Ключевые сценарии

### Сценарий 1: Создание визитки

1. Пользователь регистрируется или входит в аккаунт.
2. Нажимает «Создать визитку».
3. Заполняет имя, должность, компанию, телефон, e-mail и ссылки.
4. Загружает фото по желанию.
5. Сохраняет визитку.
6. Получает публичную ссылку и QR-код.

### Сценарий 2: Передача контакта

1. Владелец открывает QR-код на телефоне.
2. Получатель сканирует QR-код камерой.
3. Открывается публичная страница визитки.
4. Получатель нажимает «Позвонить», «Написать в WhatsApp», «Открыть Telegram» или «Сохранить контакт».
5. Контакт сохраняется через vCard либо получатель связывается напрямую.

### Сценарий 3: Обновление информации

1. Владелец меняет номер телефона или добавляет новую ссылку.
2. Сохраняет изменения.
3. Публичная страница и QR-код остаются доступными по прежней ссылке.
4. Получатель при следующем открытии видит актуальные данные.

## 6. User stories

Каждая user story должна быть независимо тестируемой и представлять законченный срез ценности. [33][34][44]

### US-01 — Регистрация и вход — P1

**Как** новый пользователь,  
**я хочу** создать аккаунт по e-mail и паролю,  
**чтобы** сохранять свои визитки и получать к ним доступ с любого устройства.

**Почему P1:** без авторизации нельзя безопасно хранить и редактировать визитки.

**Независимая проверка:** новый пользователь может зарегистрироваться, выйти из системы и войти повторно.

**Acceptance scenarios**

1. **Given** пользователь находится на странице регистрации, **When** он вводит корректный e-mail и пароль, **Then** создаётся аккаунт и пользователь попадает в личный кабинет.
2. **Given** e-mail уже зарегистрирован, **When** пользователь пытается зарегистрироваться повторно, **Then** система показывает понятную ошибку и не создаёт дубликат аккаунта.
3. **Given** зарегистрированный пользователь ввёл корректные данные, **When** он нажимает «Войти», **Then** открывается личный кабинет.
4. **Given** пользователь ввёл неверный пароль, **When** он пытается войти, **Then** система показывает сообщение об ошибке без раскрытия деталей безопасности.

### US-02 — Создание визитки — P1

**Как** владелец,  
**я хочу** создать цифровую визитку с контактами и ссылками,  
**чтобы** делиться актуальной информацией о себе.

**Почему P1:** это основная создаваемая ценность продукта.

**Независимая проверка:** пользователь создаёт карточку, заполняет поля и видит её в списке своих визиток.

**Acceptance scenarios**

1. **Given** авторизованный пользователь находится в кабинете, **When** он нажимает «Создать визитку», **Then** открывается форма создания.
2. **Given** пользователь заполнил обязательные поля, **When** он сохраняет карточку, **Then** создаётся визитка с уникальной публичной ссылкой.
3. **Given** пользователь не заполнил обязательные поля, **When** он нажимает «Сохранить», **Then** система показывает ошибки валидации и не создаёт карточку.
4. **Given** пользователь добавил несколько ссылок, **When** он сохраняет карточку, **Then** все ссылки сохраняются и отображаются в заданном порядке.

### US-03 — Публичная страница визитки — P1

**Как** получатель,  
**я хочу** открыть визитку по ссылке или QR-коду без регистрации,  
**чтобы** быстро увидеть контакты владельца.

**Почему P1:** публичный доступ без установки приложения — ключевое отличие цифрового визитника.

**Независимая проверка:** неавторизованный пользователь открывает публичную ссылку и видит карточку.

**Acceptance scenarios**

1. **Given** визитка опубликована, **When** получатель открывает `/u/{slug}`, **Then** он видит имя, фото при наличии, должность, компанию, контакты и ссылки.
2. **Given** получатель не зарегистрирован, **When** он открывает публичную ссылку, **Then** ему не требуется вход в систему.
3. **Given** slug не существует или визитка удалена, **When** получатель открывает ссылку, **Then** отображается страница 404 с понятным сообщением.
4. **Given** поле не заполнено владельцем, **When** получатель открывает карточку, **Then** это поле не отображается.

### US-04 — QR-код визитки — P1

**Как** владелец,  
**я хочу** получить QR-код своей визитки,  
**чтобы** делиться контактом при личной встрече.

**Почему P1:** QR — основной сценарий офлайн-передачи визитки.

**Независимая проверка:** пользователь открывает карточку, видит QR-код и может скачать его как изображение.

**Acceptance scenarios**

1. **Given** визитка опубликована, **When** владелец открывает страницу QR-кода, **Then** отображается QR-код, ведущий на canonical URL визитки.
2. **Given** владелец нажимает «Скачать QR», **Then** скачивается PNG или SVG с читаемым QR-кодом.
3. **Given** владелец сканирует QR-код другим устройством, **When** камера распознаёт код, **Then** открывается публичная страница визитки.
4. **Given** владелец изменил содержимое визитки, **When** он открывает прежний QR-код, **Then** QR-код по-прежнему ведёт на ту же публичную ссылку.

### US-05 — Сохранение контакта в vCard — P1

**Как** получатель,  
**я хочу** сохранить контакт владельца в адресную книгу,  
**чтобы** не вводить данные вручную.

**Почему P1:** сохранение контакта превращает просмотр страницы в полезное действие.

**Независимая проверка:** получатель скачивает vCard и импортирует её в контакты телефона.

**Acceptance scenarios**

1. **Given** получатель открыл публичную визитку, **When** он нажимает «Сохранить контакт», **Then** скачивается файл vCard.
2. **Given** vCard скачан, **When** получатель открывает его на iOS или Android, **Then** система предлагает добавить контакт в адресную книгу.
3. **Given** у владельца указаны имя, телефон и e-mail, **When** получатель сохраняет vCard, **Then** эти поля корректно отображаются в контакте.
4. **Given** у владельца нет телефона, **When** получатель скачивает vCard, **Then** файл создаётся без телефонного поля и не содержит пустых значений.

### US-06 — Быстрая связь — P1

**Как** получатель,  
**я хочу** одним нажатием позвонить, написать в WhatsApp или Telegram,  
**чтобы** сразу связаться с владельцем визитки.

**Почему P1:** прямая связь — главный сценарий после просмотра карточки.

**Независимая проверка:** на карточке отображаются только доступные каналы связи, и каждая кнопка открывает корректный протокол/ссылку.

**Acceptance scenarios**

1. **Given** указан телефон, **When** получатель нажимает «Позвонить», **Then** открывается системный набор номера.
2. **Given** указан e-mail, **When** получатель нажимает «Написать», **Then** открывается почтовый клиент с подставленным адресом.
3. **Given** указан номер WhatsApp, **When** получатель нажимает кнопку WhatsApp, **Then** открывается WhatsApp с корректным номером.
4. **Given** указан Telegram username, **When** получатель нажимает кнопку Telegram, **Then** открывается Telegram по корректной ссылке.
5. **Given** канал связи не указан, **When** получатель открывает карточку, **Then** соответствующая кнопка не отображается.

### US-07 — Редактирование визитки — P2

**Как** владелец,  
**я хочу** изменить данные визитки в любой момент,  
**чтобы** получатели всегда видели актуальную информацию.

**Почему P2:** важно после первого успешного создания карточки, но не блокирует базовый сценарий обмена контактом.

**Независимая проверка:** владелец меняет поле, сохраняет изменения и видит их на публичной странице.

**Acceptance scenarios**

1. **Given** владелец открыл свою визитку в редакторе, **When** он изменяет телефон и сохраняет форму, **Then** новое значение отображается на публичной странице.
2. **Given** владелец изменил публичную ссылку вручную, **When** он сохраняет изменения, **Then** система проверяет уникальность slug и показывает ошибку при конфликте.
3. **Given** владелец отключил публикацию визитки, **When** получатель открывает прежнюю ссылку, **Then** страница возвращает 404 или показывает сообщение о недоступности.
4. **Given** владелец удалил визитку, **When** он пытается открыть её публичную ссылку, **Then** страница возвращает 404.

### US-08 — Базовая статистика — P2

**Как** владелец,  
**я хочу** видеть просмотры и клики по своей визитке,  
**чтобы** понимать, работает ли канал распространения.

**Почему P2:** статистика повышает ценность для активных пользователей, но не нужна для первого обмена контактом.

**Независимая проверка:** владелец открывает визитку, выполняет действия и видит обновлённые счётчики.

**Acceptance scenarios**

1. **Given** получатель открыл публичную визитку, **When** страница полностью загрузилась, **Then** фиксируется событие просмотра.
2. **Given** получатель нажал кнопку WhatsApp, **When** действие выполнено, **Then** фиксируется клик с каналом `whatsapp`.
3. **Given** получатель скачал vCard, **When** файл начал скачиваться, **Then** фиксируется событие сохранения контакта.
4. **Given** владелец открыл статистику, **When** он просматривает дашборд, **Then** он видит количество просмотров, кликов по каналам и сохранений за выбранный период.

## 7. Функциональные требования

### Аккаунт и профиль

- **FR-001:** Система MUST позволять регистрацию по e-mail и паролю.
- **FR-002:** Система MUST позволять выход из аккаунта.
- **FR-003:** Система MUST ограничивать доступ к редактированию визитки её владельцем.
- **FR-004:** Система MUST поддерживать восстановление доступа через e-mail в последующей итерации; в MVP допускается ручной процесс через поддержку.

### Визитка

- **FR-005:** Система MUST позволять создавать несколько визиток для одного аккаунта.
- **FR-006:** Система MUST поддерживать поля: имя, должность, компания, краткое описание, фото, телефон, e-mail, сайт.
- **FR-007:** Система MUST поддерживать ссылки на WhatsApp, Telegram, LinkedIn, Instagram, сайт и произвольные URL.
- **FR-008:** Система MUST генерировать уникальный slug для публичной ссылки визитки.
- **FR-009:** Система MUST позволять владельцу изменить slug при соблюдении правил уникальности и формата.
- **FR-010:** Система MUST позволять публиковать, снимать с публикации, архивировать и удалять визитку.
- **FR-011:** Система MUST отображать на публичной странице только заполненные поля.
- **FR-012:** Система MUST поддерживать загрузку изображения аватара размером не более 5 MB в форматах JPEG, PNG или WebP.

### Публичный доступ

- **FR-013:** Система MUST открывать визитку по URL `/u/{slug}` без авторизации получателя.
- **FR-014:** Система MUST генерировать QR-код, ведущий на canonical URL визитки.
- **FR-015:** Система MUST предоставлять vCard для скачивания по отдельному endpoint.
- **FR-016:** Система MUST отображать кнопки только для доступных каналов связи.
- **FR-017:** Система MUST корректно обрабатывать внешние ссылки с валидными протоколами `https` и `http`.

### Аналитика

- **FR-018:** Система MUST фиксировать событие просмотра публичной визитки.
- **FR-019:** Система MUST фиксировать клики по каналам связи и внешним ссылкам.
- **FR-020:** Система MUST фиксировать скачивание vCard.
- **FR-021:** Система MUST отображать владельцу агрегированную статистику без персональных данных получателей.
- **FR-022:** Система MUST не сохранять IP-адрес, точную геолокацию или отпечаток устройства получателя в MVP.

## 8. Нефункциональные требования

| Категория | Требование |
|---|---|
| Производительность | Публичная страница визитки MUST открываться не более чем за 2 секунды на мобильном соединении 4G при стандартном размере карточки |
| Адаптивность | Интерфейс MUST корректно работать на экранах от 360 px ширины |
| Доступность | Основные действия MUST быть доступны с клавиатуры и иметь понятные текстовые подписи |
| Безопасность | Пароли MUST храниться только в защищённом хэшированном виде |
| Приватность | Публичная страница MUST раскрывать только информацию, которую владелец явно сделал доступной |
| Надёжность | Ошибка аналитики MUST не блокировать открытие визитки или скачивание vCard |
| Масштабируемость | Архитектура MUST допускать рост до 10 000 активных визиток без изменения ключевых контрактов API |
| Локализация | MVP MUST поддерживать русский язык; английский язык допускается как вторая локаль |
| SEO | Публичная страница MUST иметь корректные `title`, `description` и Open Graph metadata |

## 9. Edge cases

| Сценарий | Ожидаемое поведение |
|---|---|
| Slug уже занят | Система предлагает другой slug или показывает ошибку уникальности |
| Slug содержит запрещённые символы | Валидация отклоняет значение до сохранения |
| Фото слишком большое | Система показывает понятную ошибку и не сохраняет файл |
| Фото неподдерживаемого формата | Система отклоняет файл и указывает допустимые форматы |
| Некорректный номер телефона | Система предупреждает владельца, но не обязательно блокирует сохранение |
| Некорректная ссылка | Система показывает ошибку валидации |
| QR-код отсканирован до публикации | Система возвращает 404 |
| Владелец удалил визитку | Публичная ссылка перестаёт работать |
| Получатель открыл страницу офлайн | Базовая информация может отображаться из кэша; действия, требующие сети, показывают понятную ошибку |
| Массовые автоматические просмотры | Система применяет rate limiting и не искажает статистику бесконечными запросами |
| Длинное имя или название компании | Текст корректно переносится без разрушения вёрстки |
| Эмодзи и кириллица в полях | Символы корректно сохраняются, отображаются и попадают в vCard |
| У владельца нет ни одного канала связи | Карточка открывается, но блок действий не отображается |

## 10. Ограничения и допущения

### Допущения

- Пользователь имеет доступ к e-mail.
- Получатель имеет современный мобильный браузер.
- QR-код сканируется стандартной камерой смартфона.
- Владелец самостоятельно отвечает за достоверность размещённой информации.
- В MVP не требуется интеграция с внешними CRM, календарями или телефонными системами.

### Ограничения

- В MVP не гарантируется работа во всех устаревших браузерах.
- В MVP не предусматривается офлайн-редактирование визитки.
- В MVP не предусмотрена верификация владельца бизнеса.
- В MVP не предусмотрена автоматическая проверка ссылок на вредоносный контент.
- В MVP не гарантируется корректное поведение NFC, поскольку NFC не входит в scope.

## 11. Критерии успеха MVP

| ID | Критерий | Целевое значение |
|---|---|---|
| SC-001 | Новый пользователь может создать и опубликовать визитку | Не более чем за 5 минут |
| SC-002 | Получатель может открыть визитку по QR-коду | Без регистрации и установки приложения |
| SC-003 | Получатель может сохранить контакт | Через vCard на iOS и Android |
| SC-004 | Публичная страница открывается на мобильном устройстве | Не более чем за 2 секунды на 4G |
| SC-005 | Владелец может увидеть базовую статистику | Просмотры, клики, сохранения |
| SC-006 | Владелец может обновить информацию | Без изменения публичной ссылки |
| SC-007 | Ключевые пользовательские сценарии покрыты тестами | Не менее 90% критических acceptance scenarios |

## 13. Definition of Done

Спецификация MVP считается готовой, когда:

- [ ] Определены целевые пользователи и ключевая ценность.
- [ ] Явно указаны функции, входящие и не входящие в MVP.
- [ ] Каждая user story имеет приоритет и независимый способ проверки.
- [ ] Все acceptance scenarios сформулированы в формате Given / When / Then.
- [ ] Определены функциональные и нефункциональные требования.
- [ ] Описаны edge cases и поведение при ошибках.
- [ ] Указаны критерии успеха и ограничения.
- [ ] Открытые вопросы либо закрыты, либо имеют решение по умолчанию.
- [ ] Спецификация не содержит требований к конкретным библиотекам, БД или фреймворкам.
