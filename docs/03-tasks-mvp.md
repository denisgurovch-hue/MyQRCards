## T-003 — Управление визитками: создание, список, редактирование

### Статус
Ready

### Цель
Авторизованный пользователь может создавать и редактировать свои цифровые визитки,
просматривать их список и управлять статусом публикации.

### Предусловия
- T-001 — инфраструктура проекта завершена.
- T-002 — авторизация завершена и проверена.
- Защищённые API endpoints могут получить `currentUser.id`.

### Scope
- Модель `Card`.
- Модель `CardLink`.
- Prisma migration для карточек и ссылок.
- API для создания карточки.
- API для списка карточек текущего пользователя.
- API для получения одной карточки владельцем.
- API для редактирования карточки.
- API для публикации и снятия с публикации.
- API для архивирования и удаления карточки.
- Генерация уникального slug.
- Базовые страницы:
  - `/dashboard`
  - `/cards/new`
  - `/cards/[id]/edit`
- Валидация данных карточки.
- Unit- и integration-тесты.

### Вне scope
- Публичная страница карточки.
- QR-код.
- vCard.
- Загрузка фотографий.
- Аналитика.
- Выбор и генерация шаблонов.
- AI-функции.
- NFC.
- Корпоративные карточки и роли сотрудников.
- Оплата и тарифы.

### Поля карточки
- `displayName` — обязательное имя владельца.
- `jobTitle` — необязательная должность.
- `companyName` — необязательное название компании.
- `summary` — необязательное краткое описание.
- `phone` — необязательный телефон.
- `email` — необязательный e-mail.
- `showEmail` — по умолчанию `false`.
- `websiteUrl` — необязательная ссылка на сайт.
- `photoUrl` — nullable; загрузка файлов не реализуется в этой задаче.
- `slug` — уникальный публичный идентификатор.
- `status` — `draft`, `published`, `archived`.
- `links` — список внешних ссылок.

### Правила slug
- Допустимы только строчные латинские буквы, цифры и дефис.
- Длина: от 6 до 32 символов.
- Slug уникален без учёта регистра.
- Если пользователь не указал slug, система генерирует его из имени и случайного суффикса.
- Если выбранный slug занят, система возвращает `409 SLUG_ALREADY_EXISTS`.
- Slug карточки не меняется автоматически при редактировании имени.

### Acceptance criteria

#### Создание
- [ ] Авторизованный пользователь может создать карточку.
- [ ] Неавторизованный запрос на создание возвращает `401`.
- [ ] Обязательное поле `displayName` валидируется.
- [ ] Новая карточка создаётся со статусом `draft`.
- [ ] `showEmail` по умолчанию равен `false`.
- [ ] Если slug не задан, он генерируется автоматически.
- [ ] Повторяющийся slug возвращает `409 SLUG_ALREADY_EXISTS`.
- [ ] Ссылки карточки сохраняются в заданном порядке.

#### Список и чтение
- [ ] Пользователь получает только свои карточки.
- [ ] Список карточек поддерживает пагинацию.
- [ ] Авторизованный пользователь может получить данные своей карточки для редактирования.
- [ ] Запрос карточки другого пользователя возвращает `404`.
- [ ] Неавторизованный запрос возвращает `401`.

#### Редактирование
- [ ] Владелец может менять поля своей карточки.
- [ ] Изменение имени не меняет slug автоматически.
- [ ] Владелец может изменить slug, если новый slug валиден и свободен.
- [ ] Пользователь не может редактировать карточку другого пользователя.
- [ ] Пользователь не может передать `userId` и присвоить карточку другому аккаунту.
- [ ] `showEmail` сохраняется и возвращается в приватном API владельца.

#### Статусы
- [ ] Владелец может опубликовать карточку.
- [ ] Владелец может снять карточку с публикации, вернув её в `draft`.
- [ ] Владелец может архивировать карточку.
- [ ] Невалидный статус отклоняется с `400 VALIDATION_ERROR`.

#### Удаление
- [ ] Удаление выполняется как soft delete.
- [ ] Удалённая карточка не появляется в обычном списке.
- [ ] Удалённая карточка не доступна для редактирования.
- [ ] Связанные CardLink удаляются или каскадно помечаются удалёнными согласно модели данных.

#### Тесты
- [ ] Есть тесты на создание, чтение, редактирование и удаление.
- [ ] Есть тесты на доступ двух разных пользователей к карточкам друг друга.
- [ ] Есть тесты на уникальность и формат slug.
- [ ] Есть тесты на скрытие/сохранение `showEmail`.
- [ ] Тесты проверяют недоверенные поля и mass assignment.

### Definition of Done
- [ ] Prisma migration применяется на чистой тестовой БД.
- [ ] Все endpoints документированы в OpenAPI.
- [ ] Все DTO валидируются.
- [ ] Проверка владения карточкой выполняется на backend.
- [ ] `npm run lint` проходит.
- [ ] `npm run test` проходит.
- [ ] UI позволяет создать карточку и увидеть её в кабинете.
- [ ] UI показывает ошибки валидации и состояния загрузки.

## T-004 — Публичная страница визитки

### Статус
Ready

### Цель
Получатель открывает опубликованную визитку по ссылке `/u/{slug}`
без регистрации и установки приложения, видит разрешённые владельцем
данные и может воспользоваться доступными каналами связи.

### Предусловия
- T-003 завершена.
- Владелец может создать, изменить и опубликовать карточку.
- В модели Card существуют slug, статус публикации и признак удаления.
- Реализованы CardLink и порядок отображения ссылок.

### Scope
- Публичный API получения опубликованной карточки.
- Отдельный публичный DTO с явным списком разрешённых полей.
- Страница `/u/[slug]`.
- Один базовый адаптивный шаблон.
- Кнопки телефона, e-mail, сайта и ссылки из CardLink.
- Скрытие незаполненных полей.
- Скрытие e-mail при showEmail=false.
- Обработка недоступной карточки и ошибок API.
- Базовые metadata и canonical URL.
- Кнопки «Открыть визитку» и «Копировать ссылку» в кабинете владельца.
- Integration- и E2E-тесты.

### Вне scope
- QR-код.
- vCard и кнопка «Сохранить контакт».
- Сбор просмотров и кликов.
- Дашборд аналитики.
- Загрузка изображений.
- Офлайн-доступ и service worker.
- Выбор шаблонов, темы и AI-дизайн.
- Каталог визиток и поиск.
- Новые OAuth-провайдеры.
- Изменения архитектуры авторизации.

### Продуктовые решения для этой задачи
- Публично доступна только карточка со статусом published,
  не помеченная удалённой.
- Для draft, archived, deleted и неизвестного slug возвращается
  одинаковый ответ 404 без раскрытия причины.
- После снятия с публикации следующий новый запрос страницы
  не должен возвращать ранее опубликованную карточку.
- Старую вкладку браузера принудительно не очищаем:
  уже переданные данные невозможно отозвать.
- В этой задаче публичные карточки не индексируются:
  robots = noindex, nofollow.
- Доступ по ссылке не является защитой конфиденциальных данных:
  любая опубликованная информация доступна получателю ссылки.
- Публичный API и страница работают без пользовательской сессии.

### Публичный API

GET /api/v1/public/cards/{slug}

#### Успешный ответ: 200
{
  "card": {
    "slug": "ivan-ivanov",
    "displayName": "Иван Иванов",
    "jobTitle": "Руководитель проектов",
    "companyName": "Компания",
    "summary": "Цифровизация логистики",
    "photoUrl": null,
    "phone": "+79990000000",
    "email": null,
    "websiteUrl": "https://example.ru",
    "links": [
      {
        "type": "telegram",
        "label": "Telegram",
        "url": "https://t.me/example"
      }
    ]
  }
}

#### Правила ответа
- Использовать отдельный PublicCardDto.
- Сериализовать только явно перечисленные публичные поля.
- При showEmail=false поле email всегда равно null.
- Не возвращать userId, e-mail аккаунта, identities,
  внутренние служебные поля и данные сессии.
- Не возвращать запись Prisma через spread или напрямую.
- Ссылки возвращаются в порядке sortOrder.
- Неизвестная или недоступная карточка возвращает 404 CARD_NOT_FOUND.
- Некорректный slug возвращает тот же 404.
- Публичные ответы: Cache-Control: no-store.
- Не устанавливать auth cookies из этого endpoint.

### Страница `/u/[slug]`

#### Отображение
- Имя — главный заголовок.
- Должность, компания и описание — только если заполнены.
- Фото — только при наличии допустимого источника.
- Если фото отсутствует или не загрузилось — нейтральный placeholder.
- Длинные строки и ссылки не создают горизонтальную прокрутку.
- Пользовательский текст отображается как текст, не HTML.

#### Действия
- Телефон: ссылка tel:.
- E-mail: ссылка mailto:, только если публичный email не null.
- Сайт: валидная внешняя ссылка.
- CardLink: валидная внешняя ссылка с понятным названием.
- Внешние HTTP(S)-ссылки открываются в новой вкладке
  с rel="noopener noreferrer".
- Для tel: и mailto: новая вкладка не требуется.
- При отсутствии контактов блок действий не отображается.
- Не добавлять кнопки QR, vCard и аналитики.

#### Состояния
- Успешная загрузка.
- Карточка недоступна: понятная страница «Визитка не найдена».
- Временная ошибка API: отдельное сообщение об ошибке,
  а не ложный 404.
- Ошибка изображения не блокирует остальные данные.

### Рендеринг и кэширование
- Основная информация формируется на сервере.
- Не использовать приватный API владельца для публичной страницы.
- Не передавать пользовательские cookies и Authorization
  в публичный запрос.
- Для T-004 не использовать ISR, статическую генерацию карточек
  и межзапросный кэш их данных.
- Явно отключить кэширование публичных данных и страницы
  способом, совместимым с установленной версией Next.js.
- Не менять версию Next.js ради реализации этой задачи.
- Повторное открытие страницы после редактирования
  показывает актуальные данные.
- После изменения showEmail с true на false новый запрос
  не содержит старый e-mail.

### Metadata
- title: имя владельца и название продукта.
- description: краткое описание либо нейтральный текст
  без телефонов и e-mail.
- canonical: абсолютный URL `/u/{slug}` на основном домене продукта.
- robots: noindex, nofollow.
- Metadata формируется только из публичного DTO.
- Скрытый e-mail не должен попадать в metadata.

### Изменения кабинета владельца
- Для опубликованной карточки доступны:
  - «Открыть визитку».
  - «Копировать ссылку».
- Для неопубликованной карточки не показывать ссылку
  как работающую публичную страницу.
- При ошибке Clipboard API показать ссылку для ручного копирования.
- После копирования показать доступное текстовое подтверждение.
- URL формируется из настроенного публичного адреса продукта,
  а не внутреннего адреса API.

## T-005 — QR-код визитки: отображение и скачивание PNG/SVG

### Статус
Ready

### Цель
Владелец опубликованной визитки может:
- открыть её QR-код в кабинете;
- показать QR-код на экране телефона;
- скачать QR-код в PNG или SVG.

Получатель сканирует QR-код и открывает публичную страницу
визитки без регистрации.

### Предусловия
- T-003 — управление визитками завершена.
- T-004 — публичная страница визитки завершена.
- Настроен публичный адрес приложения.
- Публичная карточка доступна по `/u/{slug}`.

### Scope
- Серверная генерация QR-кода.
- Endpoint для PNG.
- Endpoint для SVG.
- Отображение QR-кода в кабинете владельца.
- Кнопки скачивания PNG и SVG.
- Проверка доступности карточки перед выдачей QR.
- Unit-, integration- и E2E-тесты.
- Автоматическая проверка декодирования PNG.
- Ручная проверка сканирования камерой смартфона.

### Вне scope
- vCard.
- Аналитика сканирований и скачиваний.
- Динамические редиректы и отдельные короткие ссылки.
- NFC.
- Логотип внутри QR.
- Цветовые темы и стилизация QR.
- Генерация печатной визитки или PDF.
- Массовое скачивание QR.
- Отправка QR по e-mail.
- Хранение QR-файлов в S3 или БД.
- Предпросмотр QR для черновиков и архивных карточек.

### Продуктовые решения
- QR содержит только canonical URL публичной карточки.
- Пример содержимого:
  https://public-domain.example/u/ivan-ivanov
- В QR не добавляются UTM, токены, внутренние ID,
  e-mail, телефон или другие данные карточки.
- В этой задаче QR доступен только для опубликованной,
  не удалённой карточки.
- Публичные endpoints QR работают без авторизации.
- В кабинете QR доступен через действие «QR-код».
- QR не встраивается в публичную страницу получателя.
- Изменение имени, телефона или компании не меняет URL в QR.
- Изменение slug меняет URL и делает ранее скачанный QR устаревшим.
- Поддержка старых slug и переадресация не входят в T-005.
- После снятия карточки с публикации новый запрос QR возвращает 404.
- Ранее скачанное изображение отозвать невозможно:
  оно продолжает содержать URL недоступной карточки.

### Формирование публичного URL
- Использовать существующую конфигурацию публичного адреса продукта.
- Не вводить дублирующую переменную, если подходящая уже есть.
- Если такой настройки нет, добавить PUBLIC_APP_URL
  в конфигурацию и .env.example.
- Не формировать URL из непроверенного Host или X-Forwarded-Host.
- Не использовать внутренние Docker hostname, адрес API
  или localhost в staging/production.
- Не принимать произвольный URL для кодирования из query/body.
- При некорректной конфигурации приложение должно сообщать
  об ошибке настройки, а не молча генерировать неверный QR.

### Параметры генерации
- Чёрные модули на непрозрачном белом фоне.
- Уровень коррекции ошибок: M.
- Белое поле вокруг символа: 4 модуля.
- PNG: фиксированный размер 1024 × 1024 px.
- SVG: квадратный масштабируемый документ с корректным viewBox.
- Без логотипов, произвольных цветов и дополнительных изображений.
- Не предоставлять query-параметры настройки размера,
  полей и коррекции ошибок в T-005.
- Использовать существующую QR-библиотеку, если она подходит.
- Если библиотеки нет, обосновать одну новую зависимость.
- Генерация выполняется локально на сервере,
  без стороннего API генерации QR.

### API

#### GET /api/v1/public/cards/{slug}/qr.png

Успешный ответ: 200

Headers:
- Content-Type: image/png

### Продуктовые решения

  в адресной книге получателя.
- В UI не показывать «Контакт сохранён»:
  сервис не может подтвердить фактическое сохранение.

### Поля vCard

| Поле карточки | Свойство vCard | Правило |
|---|---|---|
| displayName | FN | Обязательное отображаемое имя |
| displayName | N | См. правило структурированного имени ниже |
| companyName | ORG | Только если заполнено |
| jobTitle | TITLE | Только если заполнено |
| phone | TEL;TYPE=VOICE | Только если заполнено |
| email | EMAIL;TYPE=INTERNET | Только если showEmail=true и email заполнен |
| websiteUrl | URL | Если заполнен и допустим |
| canonical URL | URL | Ссылка на публичную визитку |
| summary | NOTE | Только если заполнено |

Не экспортировать:
- userId и внутренние ID;
- e-mail аккаунта;
- приватные настройки;
- Identity и данные сессий;
- скрытый e-mail;
- фото;
- CardLink в этой версии.

### Структурированное имя
- FN содержит displayName без изменения смысла.
- Не пытаться автоматически разделить displayName
  на фамилию, имя и отчество.
- До появления отдельных полей использовать согласованный fallback:
  N:{экранированный displayName};;;;
- Такое представление может влиять на сортировку контактов:
  это явно проверяется на реальных устройствах.
- Не добавлять новые поля ФИО в БД в рамках T-006.

### Правила сериализации
- BEGIN:VCARD и END:VCARD.
- VERSION:3.0.
- Обязательные FN и N.
- Переводы строк между свойствами: CRLF.
- Текстовые значения экранируются по правилам vCard 3.0.
- Пользовательские переводы строк не создают новые свойства vCard.
- Структурные разделители свойств не экранируются
  вместе с пользовательскими значениями.
- Длинные строки сворачиваются по правилам формата.
- Не разрывать многобайтные UTF-8 символы при сворачивании.
- Пустые необязательные свойства не добавляются.
- Не добавлять строки со значениями null или undefined.
- Не собирать файл небезопасной конкатенацией

На странице карточки добавить блок или вкладку «Аналитика»:

- Метрики: «Просмотры», «Клики», «Скачивания vCard».
- Переключатель периода: `7 дней` / `30 дней`.
- Разбивка кликов по каналам.
- Данные по дням в виде таблицы или простого графика.
- Пустое состояние: «Пока нет данных за выбранный период».
- Состояние загрузки и понятное сообщение при ошибке загрузки данных.

### API

```http

Модель данных
Добавить таблицу  card_events :

Добавить индексы, достаточные для запросов:
•	 card_id  +  occurred_at 
•	 card_id  +  day 
•	 event_type 
•	 channel 
Правила приватности и безопасности
•	Не хранить полный IP-адрес посетителя.
•	Не хранить User-Agent в сыром виде.
•	Не хранить полный URL с query-параметрами.
•	Не хранить телефон, e-mail, имя, идентификаторы устройства или иные PII в событиях аналитики.
•	Не использовать сторонние системы аналитики, рекламные пиксели или third-party cookies.
•	Не раскрывать в публичном API сырые события, IP-адреса, visitor_hash или данные посетителей.
•	Доступ к аналитике имеет только владелец карточки.
•	Для чужой карточки возвращать  404 , а не  403 .
•	Для неавторизованного запроса возвращать  401 .
•	Ошибка записи события аналитики не должна нарушать открытие публичной карточки, QR-кода или скачивание vCard.

В T-007 не реализуются:
•	Определение уникальных посетителей.
•	Геолокация, страна, город.
•	Источники трафика, UTM-метки и рефереры.
•	Воронки и конверсии.
•	Экспорт CSV.
•	Сравнение периодов.
•	Корпоративная аналитика.
•	Интеграции с Google Analytics, Яндекс.Метрикой или другими внешними сервисами.
•	Продвинутая защита от ботов и накрутки.
Acceptance criteria
•	При успешном открытии опубликованной карточки  /u/{slug}  создаётся событие  card_view .
•	При запросе несуществующего slug событие  card_view  не создаётся.
•	При открытии неопубликованной карточки событие  card_view  не создаётся.

•	При клике по e-mail создаётся событие  contact_click  с  channel=email .
•	При клике по WhatsApp создаётся событие  contact_click  с  channel=whatsapp .
•	При клике по Telegram создаётся событие  contact_click  с  channel=telegram .

•	При успешном скачивании vCard создаётся событие  vcard_download  с  channel=vcard .
•	Владелец может получить аналитику своей карточки за 7 дней.
•	Владелец может получить аналитику своей карточки за 30 дней.
•	API возвращает  totals ,  by_channel  и  daily .
•	Сумма событий в  daily  соответствует значениям в  totals .
•	Владелец не видит аналитику чужой карточки; запрос возвращает  404 .
•	Неавторизованный запрос аналитики возвращает  401 .
•	Публичный посетитель не может получить аналитику карточки.
•	В кабинете отображаются просмотры, клики, скачивания vCard, разбивка по каналам и данные по дням.
•	При отсутствии событий отображается пустое состояние.
•	Ошибка аналитики не мешает открытию публичной визитки или скачиванию vCard.
•	В БД не сохраняются полный IP, сырой User-Agent, query-параметры URL и PII посетителей.
Definition of Done
•	Реализована модель/таблица  card_events  и необходимые миграции.
•	Реализована запись событий  card_view ,  contact_click  и  vcard_download .

•	Реализованы периоды  7d  и  30d .
•	Реализованы агрегации по дням и каналам.
•	Проверен доступ владельца к аналитике только своей карточки.
•	Добавлены unit- и/или integration-тесты для записи событий и API аналитики.
•	Добавлены тесты на запрет доступа к чужой аналитике и неавторизованный доступ.

•	Повторные просмотры и клики на MVP допускается учитывать как отдельные события.
•	Не обязательно внедрять дедупликацию по visitor_hash в этой задаче.
•	Если visitor_hash используется, он должен быть необратимым псевдонимом, а не IP, cookie ID, device ID или fingerprint.

## T-012 — Загрузка фото в визитку

### Статус

Done

### Зависимости

- T-003 — создание и редактирование цифровых визиток работает.
- T-004 — публичная страница визитки работает.
- T-007 — базовая аналитика реализована или находится в реализации.

### Цель

Владелец цифровой визитки может загрузить своё фото и отобразить его на публичной странице визитки.

Фото делает карточку более узнаваемой и повышает доверие получателя: он видит, кому принадлежат контакты и ссылки.

### User story

Как владелец цифровой визитки,  
я хочу загрузить своё фото,  
чтобы получатель мог визуально идентифицировать меня на публичной карточке.

### Scope

#### Что реализуем

- Поле «Фото» в редакторе визитки.
- Загрузка изображения с устройства пользователя.
- Предварительный просмотр выбранного фото до сохранения.
- Клиентское выравнивание фото относительно квадратной рамки (pan + zoom) перед сохранением.
- Валидация типа, размера и размеров изображения.
- Сохранение оптимизированной версии изображения.
- Отображение фото на публичной странице визитки.
- Возможность заменить текущее фото.
- Возможность удалить фото.
- Публичная карточка корректно отображает состояние «фото не загружено».

#### Форматы и ограничения

Для MVP разрешены только растровые изображения:

- JPEG / JPG — `image/jpeg`
- PNG — `image/png`
- WebP — `image/webp`

Ограничения:

- Максимальный размер исходного файла: 5 MB.
- Максимальное разрешение: 4000 × 4000 пикселей.
- Минимальное рекомендуемое разрешение: 400 × 400 пикселей.
- На сервере создаётся оптимизированная версия изображения.
- Хранится сгенерированное приложением имя файла, а не оригинальное имя, присланное пользователем.
- Фото должно быть доступно только через безопасный URL, а не через прямой путь к файловой системе сервера.

### Интерфейс

В редакторе визитки добавить блок «Фото»:

- Кнопка «Загрузить фото».
- Предварительный просмотр выбранного изображения.
- Индикатор загрузки.
- Кнопка «Заменить фото».
- Кнопка «Удалить фото».
- Понятные сообщения об ошибках валидации.
- Сохранение изменения только после успешной загрузки и подтверждения пользователем.

На публичной странице:

- Фото отображается в карточке, если оно загружено.
- Если фото отсутствует, отображается нейтральный placeholder с инициалами владельца или стандартной иконкой.
- Некорректное или недоступное изображение не должно ломать страницу визитки.

### API

#### Загрузка фото

```http
POST /api/cards/{card_id}/photo
Content-Type: multipart/form-data
Authorization: Bearer <access_token>

Поле формы:
photo: <файл изображения>

Успешный ответ:
{
  "photo": {
    "id": "img_01H...",
    "url": "[https://smartvizitka.ru/media/cards/img_01H....webp](https://smartvizitka.ru/media/cards/img_01H....webp)",
    "width": 800,
    "height": 800,
    "mime_type": "image/webp"
  }
}

Удаление фото
DELETE /api/cards/{card_id}/photo
Authorization: Bearer <access_token>

Успешный ответ:
{
  "photo": null
}

Модель данных
Добавить в карточку связь с изображением либо отдельную таблицу  card_photos .
Рекомендуемая структура  card_photos :
| Поле        | Тип           | Описание                               |
| ----------- | ------------- | -------------------------------------- |
| id          | UUID / bigint | Идентификатор изображения              |
| card_id     | FK            | Владелец изображения                   |
| storage_key | varchar       | Сгенерированный ключ файла в хранилище |
| mime_type   | varchar       | Фактический MIME-тип после валидации   |
| width       | integer       | Ширина изображения                     |
| height      | integer       | Высота изображения                     |
| size_bytes  | bigint        | Размер сохранённого файла              |
| created_at  | timestamptz   | Дата загрузки                          |

В таблице  cards  добавить или использовать связь:
photo_id -> card_photos.id

Обработка изображения
1.	Проверить, что пользователь авторизован и является владельцем карточки.
2.	Проверить размер файла до обработки.
3.	Проверить расширение и MIME-тип, но не считать их достаточной защитой.
4.	Проверить фактическое содержимое файла по сигнатуре / magic bytes.
5.	Проверить размеры изображения в пикселях.
6.	Декодировать изображение безопасной библиотекой.
7.	Создать оптимизированную копию в формате WebP.
8.	Удалить EXIF, GPS и другие потенциально чувствительные метаданные.
9.	Сохранить файл под новым сгенерированным именем.
10.	Обновить связь карточки с изображением.
11.	При замене удалить или деактивировать предыдущий файл, чтобы не накапливать неиспользуемые изображения.
Правила безопасности
•	Загружать фото может только владелец карточки.
•	Нельзя доверять имени файла, Content-Type и расширению, присланным клиентом.
•	Нельзя сохранять оригинальное имя файла в URL или использовать его в файловой системе.
•	Нельзя разрешать SVG в MVP: SVG является XML-документом и может содержать JavaScript; при прямом открытии или встраивании это создаёт риск XSS. 
•	Нельзя разрешать HTML, JS, PDF, архивы и исполняемые файлы.
•	Нельзя сохранять загруженные файлы в webroot без безопасной обработки и контроля доступа.
•	Нужен лимит на размер файла, разрешение и количество загрузок, чтобы пользователь не мог заполнить хранилище или вызвать отказ в обслуживании. 
•	Ошибку обработки изображения нужно логировать без публикации чувствительных данных пользователя.
Ограничения
В T-012 не реализуются:
•	Кроп и редактирование фото.
•	Фильтры и ретушь.
•	Загрузка нескольких фотографий.
•	Галерея изображений.
•	Логотип компании.
•	Загрузка изображений по URL.
•	Загрузка через drag-and-drop.
•	Автоматическое распознавание лиц.
•	Модерация контента.
•	Хранение в S3 / Object Storage, если текущая инфраструктура это не предполагает.
Acceptance criteria

•	После успешной загрузки фото отображается в редакторе.
•	После сохранения фото отображается на публичной странице визитки.

•	Файл больше 5 MB отклоняется с понятным сообщением.
•	Файл неподдерживаемого формата отклоняется.
•	Файл с подделанным расширением или Content-Type отклоняется, если его содержимое не является допустимым изображением.
•	Изображение больше 4000 × 4000 пикселей отклоняется или безопасно уменьшается согласно выбранному правилу.

•	Владелец может удалить фото.
•	После удаления фото публичная карточка показывает placeholder.

•	Запрос к чужой карточке возвращает  404 .
