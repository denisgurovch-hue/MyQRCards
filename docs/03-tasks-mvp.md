## T-003 — Управление визитками: создание, список, редактирование

### Статус
Ready

### Цель
Авторизованный пользователь может создавать и редактировать свои цифровые визитки,
просматривать их список и управлять статусом публикации.

### Предусловия
- T-001 — инфраструктура проекта завершена.
- T-002 — авторизация завершена и проверена.
- Защищённые API endpoints могут получить `currentUser.id`.

### Scope
- Модель `Card`.
- Модель `CardLink`.
- Prisma migration для карточек и ссылок.
- API для создания карточки.
- API для списка карточек текущего пользователя.
- API для получения одной карточки владельцем.
- API для редактирования карточки.
- API для публикации и снятия с публикации.
- API для архивирования и удаления карточки.
- Генерация уникального slug.
- Базовые страницы:
  - `/dashboard`
  - `/cards/new`
  - `/cards/[id]/edit`
- Валидация данных карточки.
- Unit- и integration-тесты.

### Вне scope
- Публичная страница карточки.
- QR-код.
- vCard.
- Загрузка фотографий.
- Аналитика.
- Выбор и генерация шаблонов.
- AI-функции.
- NFC.
- Корпоративные карточки и роли сотрудников.
- Оплата и тарифы.

### Поля карточки
- `displayName` — обязательное имя владельца.
- `jobTitle` — необязательная должность.
- `companyName` — необязательное название компании.
- `summary` — необязательное краткое описание.
- `phone` — необязательный телефон.
- `email` — необязательный e-mail.
- `showEmail` — по умолчанию `false`.
- `websiteUrl` — необязательная ссылка на сайт.
- `photoUrl` — nullable; загрузка файлов не реализуется в этой задаче.
- `slug` — уникальный публичный идентификатор.
- `status` — `draft`, `published`, `archived`.
- `links` — список внешних ссылок.

### Правила slug
- Допустимы только строчные латинские буквы, цифры и дефис.
- Длина: от 6 до 32 символов.
- Slug уникален без учёта регистра.
- Если пользователь не указал slug, система генерирует его из имени и случайного суффикса.
- Если выбранный slug занят, система возвращает `409 SLUG_ALREADY_EXISTS`.
- Slug карточки не меняется автоматически при редактировании имени.

### Acceptance criteria

#### Создание
- [ ] Авторизованный пользователь может создать карточку.
- [ ] Неавторизованный запрос на создание возвращает `401`.
- [ ] Обязательное поле `displayName` валидируется.
- [ ] Новая карточка создаётся со статусом `draft`.
- [ ] `showEmail` по умолчанию равен `false`.
- [ ] Если slug не задан, он генерируется автоматически.
- [ ] Повторяющийся slug возвращает `409 SLUG_ALREADY_EXISTS`.
- [ ] Ссылки карточки сохраняются в заданном порядке.

#### Список и чтение
- [ ] Пользователь получает только свои карточки.
- [ ] Список карточек поддерживает пагинацию.
- [ ] Авторизованный пользователь может получить данные своей карточки для редактирования.
- [ ] Запрос карточки другого пользователя возвращает `404`.
- [ ] Неавторизованный запрос возвращает `401`.

#### Редактирование
- [ ] Владелец может менять поля своей карточки.
- [ ] Изменение имени не меняет slug автоматически.
- [ ] Владелец может изменить slug, если новый slug валиден и свободен.
- [ ] Пользователь не может редактировать карточку другого пользователя.
- [ ] Пользователь не может передать `userId` и присвоить карточку другому аккаунту.
- [ ] `showEmail` сохраняется и возвращается в приватном API владельца.

#### Статусы
- [ ] Владелец может опубликовать карточку.
- [ ] Владелец может снять карточку с публикации, вернув её в `draft`.
- [ ] Владелец может архивировать карточку.
- [ ] Невалидный статус отклоняется с `400 VALIDATION_ERROR`.

#### Удаление
- [ ] Удаление выполняется как soft delete.
- [ ] Удалённая карточка не появляется в обычном списке.
- [ ] Удалённая карточка не доступна для редактирования.
- [ ] Связанные CardLink удаляются или каскадно помечаются удалёнными согласно модели данных.

#### Тесты
- [ ] Есть тесты на создание, чтение, редактирование и удаление.
- [ ] Есть тесты на доступ двух разных пользователей к карточкам друг друга.
- [ ] Есть тесты на уникальность и формат slug.
- [ ] Есть тесты на скрытие/сохранение `showEmail`.
- [ ] Тесты проверяют недоверенные поля и mass assignment.

### Definition of Done
- [ ] Prisma migration применяется на чистой тестовой БД.
- [ ] Все endpoints документированы в OpenAPI.
- [ ] Все DTO валидируются.
- [ ] Проверка владения карточкой выполняется на backend.
- [ ] `npm run lint` проходит.
- [ ] `npm run test` проходит.
- [ ] UI позволяет создать карточку и увидеть её в кабинете.
- [ ] UI показывает ошибки валидации и состояния загрузки.

## T-004 — Публичная страница визитки

### Статус
Ready

### Цель
Получатель открывает опубликованную визитку по ссылке `/u/{slug}`
без регистрации и установки приложения, видит разрешённые владельцем
данные и может воспользоваться доступными каналами связи.

### Предусловия
- T-003 завершена.
- Владелец может создать, изменить и опубликовать карточку.
- В модели Card существуют slug, статус публикации и признак удаления.
- Реализованы CardLink и порядок отображения ссылок.

### Scope
- Публичный API получения опубликованной карточки.
- Отдельный публичный DTO с явным списком разрешённых полей.
- Страница `/u/[slug]`.
- Один базовый адаптивный шаблон.
- Кнопки телефона, e-mail, сайта и ссылки из CardLink.
- Скрытие незаполненных полей.
- Скрытие e-mail при showEmail=false.
- Обработка недоступной карточки и ошибок API.
- Базовые metadata и canonical URL.
- Кнопка «Открыть визитку» в кабинете владельца.
- Integration- и E2E-тесты.

### Вне scope
- QR-код.
- vCard и кнопка «Сохранить контакт».
- Сбор просмотров и кликов.
- Дашборд аналитики.
- Загрузка изображений.
- Офлайн-доступ и service worker.
- Выбор шаблонов, темы и AI-дизайн.
- Каталог визиток и поиск.
- Новые OAuth-провайдеры.
- Изменения архитектуры авторизации.

### Продуктовые решения для этой задачи
- Публично доступна только карточка со статусом published,
  не помеченная удалённой.
- Для draft, archived, deleted и неизвестного slug возвращается
  одинаковый ответ 404 без раскрытия причины.
- После снятия с публикации следующий новый запрос страницы
  не должен возвращать ранее опубликованную карточку.
- Старую вкладку браузера принудительно не очищаем:
  уже переданные данные невозможно отозвать.
- В этой задаче публичные карточки не индексируются:
  robots = noindex, nofollow.
- Доступ по ссылке не является защитой конфиденциальных данных:
  любая опубликованная информация доступна получателю ссылки.
- Публичный API и страница работают без пользовательской сессии.

### Публичный API

GET /api/v1/public/cards/{slug}

#### Успешный ответ: 200
{
  "card": {
    "slug": "ivan-ivanov",
    "displayName": "Иван Иванов",
    "jobTitle": "Руководитель проектов",
    "companyName": "Компания",
    "summary": "Цифровизация логистики",
    "photoUrl": null,
    "phone": "+79990000000",
    "email": null,
    "websiteUrl": "https://example.ru",
    "links": [
      {
        "type": "telegram",
        "label": "Telegram",
        "url": "https://t.me/example"
      }
    ]
  }
}

#### Правила ответа
- Использовать отдельный PublicCardDto.
- Сериализовать только явно перечисленные публичные поля.
- При showEmail=false поле email всегда равно null.
- Не возвращать userId, e-mail аккаунта, identities,
  внутренние служебные поля и данные сессии.
- Не возвращать запись Prisma через spread или напрямую.
- Ссылки возвращаются в порядке sortOrder.
- Неизвестная или недоступная карточка возвращает 404 CARD_NOT_FOUND.
- Некорректный slug возвращает тот же 404.
- Публичные ответы: Cache-Control: no-store.
- Не устанавливать auth cookies из этого endpoint.

### Страница `/u/[slug]`

#### Отображение
- Имя — главный заголовок.
- Должность, компания и описание — только если заполнены.
- Фото — только при наличии допустимого источника.
- Если фото отсутствует или не загрузилось — нейтральный placeholder.
- Длинные строки и ссылки не создают горизонтальную прокрутку.
- Пользовательский текст отображается как текст, не HTML.

#### Действия
- Телефон: ссылка tel:.
- E-mail: ссылка mailto:, только если публичный email не null.
- Сайт: валидная внешняя ссылка.
- CardLink: валидная внешняя ссылка с понятным названием.
- Внешние HTTP(S)-ссылки открываются в новой вкладке
  с rel="noopener noreferrer".
- Для tel: и mailto: новая вкладка не требуется.
- При отсутствии контактов блок действий не отображается.
- Не добавлять кнопки QR, vCard и аналитики.

#### Состояния
- Успешная загрузка.
- Карточка недоступна: понятная страница «Визитка не найдена».
- Временная ошибка API: отдельное сообщение об ошибке,
  а не ложный 404.
- Ошибка изображения не блокирует остальные данные.

### Рендеринг и кэширование
- Основная информация формируется на сервере.
- Не использовать приватный API владельца для публичной страницы.
- Не передавать пользовательские cookies и Authorization
  в публичный запрос.
- Для T-004 не использовать ISR, статическую генерацию карточек
  и межзапросный кэш их данных.
- Явно отключить кэширование публичных данных и страницы
  способом, совместимым с установленной версией Next.js.
- Не менять версию Next.js ради реализации этой задачи.
- Повторное открытие страницы после редактирования
  показывает актуальные данные.
- После изменения showEmail с true на false новый запрос
  не содержит старый e-mail.

### Metadata
- title: имя владельца и название продукта.
- description: краткое описание либо нейтральный текст
  без телефонов и e-mail.
- canonical: абсолютный URL `/u/{slug}` на основном домене продукта.
- robots: noindex, nofollow.
- Metadata формируется только из публичного DTO.
- Скрытый e-mail не должен попадать в metadata.

### Изменения кабинета владельца
- Для опубликованной карточки доступна «Открыть визитку».
- Для неопубликованной карточки не показывать ссылку
  как работающую публичную страницу.
- URL формируется из настроенного публичного адреса продукта,
  а не внутреннего адреса API.

## T-005 — QR-код визитки: отображение и скачивание PNG/SVG

### Статус
Ready

### Цель
Владелец опубликованной визитки может:
- открыть её QR-код в кабинете;
- показать QR-код на экране телефона;
- скачать QR-код в PNG или SVG.

Получатель сканирует QR-код и открывает публичную страницу
визитки без регистрации.

### Предусловия
- T-003 — управление визитками завершена.
- T-004 — публичная страница визитки завершена.
- Настроен публичный адрес приложения.
- Публичная карточка доступна по `/u/{slug}`.

### Scope
- Серверная генерация QR-кода.
- Endpoint для PNG.
- Endpoint для SVG.
- Отображение QR-кода в кабинете владельца.
- Кнопки скачивания PNG и SVG.
- Проверка доступности карточки перед выдачей QR.
- Unit-, integration- и E2E-тесты.
- Автоматическая проверка декодирования PNG.
- Ручная проверка сканирования камерой смартфона.

### Вне scope
- vCard.
- Аналитика сканирований и скачиваний.
- Динамические редиректы и отдельные короткие ссылки.
- NFC.
- Логотип внутри QR.
- Цветовые темы и стилизация QR.
- Генерация печатной визитки или PDF.
- Массовое скачивание QR.
- Отправка QR по e-mail.
- Хранение QR-файлов в S3 или БД.
- Предпросмотр QR для черновиков и архивных карточек.

### Продуктовые решения
- QR содержит только canonical URL публичной карточки.
- Пример содержимого:
  https://public-domain.example/u/ivan-ivanov
- В QR не добавляются UTM, токены, внутренние ID,
  e-mail, телефон или другие данные карточки.
- В этой задаче QR доступен только для опубликованной,
  не удалённой карточки.
- Публичные endpoints QR работают без авторизации.
- В кабинете QR доступен через действие «QR-код».
- QR не встраивается в публичную страницу получателя.
- Изменение имени, телефона или компании не меняет URL в QR.
- Изменение slug меняет URL и делает ранее скачанный QR устаревшим.
- Поддержка старых slug и переадресация не входят в T-005.
- После снятия карточки с публикации новый запрос QR возвращает 404.
- Ранее скачанное изображение отозвать невозможно:
  оно продолжает содержать URL недоступной карточки.

### Формирование публичного URL
- Использовать существующую конфигурацию публичного адреса продукта.
- Не вводить дублирующую переменную, если подходящая уже есть.
- Если такой настройки нет, добавить PUBLIC_APP_URL
  в конфигурацию и .env.example.
- Не формировать URL из непроверенного Host или X-Forwarded-Host.
- Не использовать внутренние Docker hostname, адрес API
  или localhost в staging/production.
- Не принимать произвольный URL для кодирования из query/body.
- При некорректной конфигурации приложение должно сообщать
  об ошибке настройки, а не молча генерировать неверный QR.

### Параметры генерации
- Чёрные модули на непрозрачном белом фоне.
- Уровень коррекции ошибок: M.
- Белое поле вокруг символа: 4 модуля.
- PNG: фиксированный размер 1024 × 1024 px.
- SVG: квадратный масштабируемый документ с корректным viewBox.
- Без логотипов, произвольных цветов и дополнительных изображений.
- Не предоставлять query-параметры настройки размера,
  полей и коррекции ошибок в T-005.
- Использовать существующую QR-библиотеку, если она подходит.
- Если библиотеки нет, обосновать одну новую зависимость.
- Генерация выполняется локально на сервере,
  без стороннего API генерации QR.

### API

#### GET /api/v1/public/cards/{slug}/qr.png

Успешный ответ: 200

Headers:
- Content-Type: image/png
- Content-Disposition: attachment; filename="qrcard-{slug}.png"
- Cache-Control: no-store
- X-Content-Type-Options: nosniff

Body:
- Бинарное PNG-изображение.

#### GET /api/v1/public/cards/{slug}/qr.svg

Успешный ответ: 200

Headers:

### Продуктовые решения
- Формат: vCard 3.0, UTF-8.
- Содержимое формируется из текущих публичных данных карточки.
- Endpoint доступен без регистрации.

- Уже скачанный файл нельзя отозвать или автоматически обновить.
- Повторное скачивание не гарантирует отсутствие дубликатов
  в адресной книге получателя.
- В UI не показывать «Контакт сохранён»:
  сервис не может подтвердить фактическое сохранение.

### Поля vCard

| Поле карточки | Свойство vCard | Правило |
|---|---|---|
| displayName | FN | Обязательное отображаемое имя |
| displayName | N | См. правило структурированного имени ниже |
| companyName | ORG | Только если заполнено |
| jobTitle | TITLE | Только если заполнено |
| phone | TEL;TYPE=VOICE | Только если заполнено |
| email | EMAIL;TYPE=INTERNET | Только если showEmail=true и email заполнен |
| websiteUrl | URL | Если заполнен и допустим |
| canonical URL | URL | Ссылка на публичную визитку |
| summary | NOTE | Только если заполнено |
| photo (файл) | PHOTO;ENCODING=b;TYPE=JPEG | Только если есть фото; см. T-019 |

Не экспортировать:
- userId и внутренние ID;
- e-mail аккаунта;
- приватные настройки;
- Identity и данные сессий;
- скрытый e-mail;
- фото;
- CardLink в этой версии.

### Структурированное имя
- FN содержит displayName без изменения смысла.
- Не пытаться автоматически разделить displayName
  на фамилию, имя и отчество.
- До появления отдельных полей использовать согласованный fallback:
  N:{экранированный displayName};;;;
- Такое представление может влиять на сортировку контактов:
  это явно проверяется на реальных устройствах.
- Не добавлять новые поля ФИО в БД в рамках T-006.

### Правила сериализации
- BEGIN:VCARD и END:VCARD.
- VERSION:3.0.
- Обязательные FN и N.
- Переводы строк между свойствами: CRLF.
- Текстовые значения экранируются по правилам vCard 3.0.
- Пользовательские переводы строк не создают новые свойства vCard.
- Структурные разделители свойств не экранируются
  вместе с пользовательскими значениями.
- Длинные строки сворачиваются по правилам формата.

- Пустые необязательные свойства не добавляются.
- Не добавлять строки со значениями null или undefined.
- Не собирать файл небезопасной конкатенацией

#### Данные аналитики

- Общее количество просмотров карточки за период.

## T-012 — Загрузка фото в визитку

### Статус

Done

### Зависимости

- T-003 — создание и редактирование цифровых визиток работает.
- T-004 — публичная страница визитки работает.
- T-007 — базовая аналитика реализована или находится в реализации.

### Цель

Владелец цифровой визитки может загрузить своё фото и отобразить его на публичной странице визитки.

Фото делает карточку более узнаваемой и повышает доверие получателя: он видит, кому принадлежат контакты и ссылки.

### User story

Как владелец цифровой визитки,  
я хочу загрузить своё фото,  
чтобы получатель мог визуально идентифицировать меня на публичной карточке.

### Scope

#### Что реализуем

- Поле «Фото» в редакторе визитки.
- Загрузка изображения с устройства пользователя.
- Предварительный просмотр выбранного фото до сохранения.
- Клиентское выравнивание фото относительно квадратной рамки (pan + zoom) перед сохранением.
- Валидация типа, размера и размеров изображения.
- Сохранение оптимизированной версии изображения.
- Отображение фото на публичной странице визитки.
- Возможность заменить текущее фото.
- Возможность удалить фото.
- Публичная карточка корректно отображает состояние «фото не загружено».

#### Форматы и ограничения

Для MVP разрешены только растровые изображения:

- JPEG / JPG — `image/jpeg`
- PNG — `image/png`
- WebP — `image/webp`

Ограничения:

- Максимальный размер исходного файла: 5 MB.
- Максимальное разрешение: 4000 × 4000 пикселей.
- Минимальное рекомендуемое разрешение: 400 × 400 пикселей.
- На сервере создаётся оптимизированная версия изображения.
- Хранится сгенерированное приложением имя файла, а не оригинальное имя, присланное пользователем.
- Фото должно быть доступно только через безопасный URL, а не через прямой путь к файловой системе сервера.

### Интерфейс

В редакторе визитки добавить блок «Фото»:

- Кнопка «Загрузить фото».
- Предварительный просмотр выбранного изображения.
- Индикатор загрузки.
- Кнопка «Заменить фото».
- Кнопка «Удалить фото».
- Понятные сообщения об ошибках валидации.
- Сохранение изменения только после успешной загрузки и подтверждения пользователем.

На публичной странице:

- Фото отображается в карточке, если оно загружено.
- Если фото отсутствует, отображается нейтральный placeholder с инициалами владельца или стандартной иконкой.
- Некорректное или недоступное изображение не должно ломать страницу визитки.

### API

Обработка изображения
1.	Проверить, что пользователь авторизован и является владельцем карточки.
2.	Проверить размер файла до обработки.
3.	Проверить расширение и MIME-тип, но не считать их достаточной защитой.
4.	Проверить фактическое содержимое файла по сигнатуре / magic bytes.

6.	Декодировать изображение безопасной библиотекой.

10.	Обновить связь карточки с изображением.

Правила безопасности
•	Загружать фото может только владелец карточки.
•	Нельзя доверять имени файла, Content-Type и расширению, присланным клиентом.

•	Нельзя сохранять загруженные файлы в webroot без безопасной обработки и контроля доступа.
•	Нужен лимит на размер файла, разрешение и количество загрузок, чтобы пользователь не мог заполнить хранилище или вызвать отказ в обслуживании.

## T-013 — Заменить «Показать QR код» на «Показать визитку»

### Статус
Done

### Цель
Заменить отдельный режим показа QR-кода полноценным презентационным
экраном визитки, который владелец может показать собеседнику
на телефоне или компьютере.

Сохранить разграничение:
- «Показать визитку» — приватный экран презентации для владельца.
- «Открыть визитку» — существующая публичная страница `/u/{slug}`,
  доступная получателю без авторизации.

### Контекст
Сейчас в личном кабинете существуют два действия:
- «Показать QR код» — открывает QR-код.
- «Открыть визитку» — открывает публичную страницу карточки.

Изолированный показ QR-кода недостаточно презентабелен.
Вместо него нужен экран, объединяющий визуальную карточку,
публичные контакты и QR-код в едином стиле приложения.

Экран презентации не заменяет публичную страницу и не должен
превращаться в её полную копию с дополнительными действиями владельца.

### Предусловия
- Работают авторизация и проверка владельца карточки.
- Реализованы управление карточками и статусы публикации.
- Работает публичная страница `/u/{slug}`.
- Работают генерация и скачивание QR в PNG и SVG.
- Есть существующий стиль главной страницы:
  компоненты, цвета, типографика, отступы и визуальные паттерны.
- Есть правила публичной видимости контактных данных.

### Scope
- Замена действия «Показать QR код» на «Показать визитку».
- Отдельный адресуемый экран презентации карточки.
- Проверка доступа к экрану только для владельца.
- Визуальная карточка в стиле главной страницы приложения.
- Отображение поддерживаемых публичных контактов и ссылок.
- QR-код опубликованной визитки.
- Публичная ссылка опубликованной визитки.
- Скачивание QR в PNG и SVG через существующий механизм.
- Действие «Открыть визитку».
- Предпросмотр неопубликованной карточки без публичных действий.
- Состояния загрузки, отсутствия доступа и ошибок.
- Адаптивность и доступность.
- Тесты и актуализация документации.

- Изменение формата, содержимого и правил генерации vCard.
- Кастомизация дизайна карточки.
- Новые темы, фоновые изображения и AI-дизайн.

- Новая админ-панель.

- Новые способы публикации или статусы карточки.
- Новые правила генерации QR.
- Новые события аналитики.
- Отдельная публичная ссылка на презентационный экран.

### Разграничение экранов

#### Презентационный экран
- Открывается действием «Показать визитку».
- Доступен только авторизованному владельцу карточки.
- Предназначен для показа с экрана устройства владельца.
- Содержит компактную визуальную карточку и блок передачи контакта.
- Не является адресом, который кодируется в QR.
- Не становится публичным из-за наличия URL.
- Не содержит форм редактирования, статистики или админ-панели.

#### Публичная страница
- Существующий маршрут `/u/{slug}`.
- Открывается действием «Открыть визитку».
- Именно её URL содержится в QR.
- Доступна получателю по существующим правилам публикации.
- Не меняется в рамках T-013.
- Не получает элементы управления владельца.

### Маршрут
Предлагаемый маршрут презентационного экрана:
`/cards/[id]/present`.

Перед реализацией:
- проверить существующую структуру маршрутов;
- использовать уже принятые в проекте соглашения;
- если выбран другой путь, зафиксировать его в документации.

Маршрут использует идентификатор карточки, а не публичный slug,
чтобы смена slug не меняла адрес экрана владельца.

### Содержимое презентационного экрана

#### Визуальная карточка
- Имя владельца.
- Фото или существующий placeholder.
- Должность, если заполнена.
- Компания, если заполнена.
- Краткое описание, если заполнено.
- Основные контакты, разрешённые к публичному показу.
- Поддерживаемые ссылки и внешние сервисы,
  разрешённые к отображению.

#### Блок передачи контакта для published-карточки
- QR-код.
- Актуальная публичная ссылка.
- «Скачать PNG».
- «Скачать SVG».
- «Открыть визитку».
- Если копирование ссылки уже реализовано, переиспользовать
  существующее действие без создания нового механизма.

#### Навигация владельца
- Понятное действие возврата в список визиток.
- Никаких форм редактирования или статистики на самом экране.

### Визуальные требования
- Переиспользовать стиль существующей главной страницы:
  цвета, шрифты, радиусы, тени, отступы и компоненты.
- Не создавать новую независимую дизайн-систему.
- Не переносить маркетинговые секции главной страницы
  на экран презентации.
- Визуальная карточка и QR должны восприниматься
  как единая композиция.
- QR должен оставаться контрастным и иметь сохранённые белые поля.
- На мобильном экране карточка и QR располагаются
  без горизонтальной прокрутки.
- На desktop допустима двухколоночная композиция.
- Длинные имена, компании и URL не ломают вёрстку.
- Не уменьшать QR ради размещения всех элементов
  в одном экране ценой читаемости.
- Не требовать обязательного полноэкранного browser API.

### Контакты и приватность
- Использовать только существующие данные карточки.
- Применять существующие правила публичной видимости.
- При showEmail=false не показывать e-mail карточки,
  даже несмотря на то, что экран открыт владельцем.
- Не показывать e-mail аккаунта вместо e-mail карточки.
- Не отображать приватные поля через fallback.
- Не выводить незаполненные поля и пустые кнопки.
- Не исполнять пользовательский HTML.
- Использовать существующие правила безопасных URL.
- Не добавлять vCard на экран презентации в рамках этой задачи.

### QR и публичная ссылка
- Переиспользовать существующий сервис и endpoints QR.
- QR содержит canonical URL `/u/{slug}`.
- QR не содержит URL приватного презентационного экрана.
- Публичная ссылка формируется существующим механизмом,
  без дублирующей переменной окружения.
- После изменения slug новый показ экрана использует новый URL.
- PNG и SVG соответствуют текущему QR.
- Ошибочный JSON не скачивается как изображение.
- Не генерировать рабочий QR для неопубликованной карточки.
- Не обходить проверку published через приватный endpoint.

### Поведение по статусам

| Состояние | Экран презентации | QR и скачивание | Публичная ссылка / открытие |
|---|---|---|---|
| published | Доступен владельцу | Доступны | Доступны |
| draft | Предпросмотр владельца | Недоступны | Недоступны |
| archived | Предпросмотр владельца | Недоступны | Недоступны |
| deleted | Недоступен | Недоступны | Недоступны |

Для draft и archived:
- Показывать визуальную карточку в режиме предпросмотра.
- Применять те же правила видимости контактов.
- Показывать сообщение:
  «Предпросмотр. Визитка не опубликована —
  QR-код и публичная ссылка недоступны».
- Не отображать кликабельную или копируемую публичную ссылку.
- Не показывать ранее загруженный QR как действующий.
- Не добавлять публикацию карточки на этот экран:
  использовать существующий кабинет.

### Снятие с публикации во время просмотра
- При новом запросе или повторном открытии экран
  должен учитывать актуальный статус.
- Если запрос QR или скачивания вернул 404,
  убрать QR и публичные действия из текущего интерфейса
  и показать состояние недоступности.
- Не показывать успешное скачивание при ошибке.
- Постоянный polling и синхронизация в реальном времени
  не входят в scope.
- Уже показанные или скачанные изображения
  принудительно отозвать невозможно.

### Авторизация и доступ
- Неавторизованный пользователь не получает данные карточки
  через презентационный маршрут или его API.
- Для страницы использовать существующее поведение
  защищённых маршрутов: например, переход на login.
- Для API без сессии возвращать 401.
- Авторизованный пользователь не может открыть
  презентацию чужой карточки.
- Чужая, неизвестная и удалённая карточки возвращают
  одинаковое состояние 404.
- Владение проверяется на backend,
  а не только через скрытие кнопки в UI.
- Не доверять ownerId/userId из query или body.
- Не кэшировать приватную страницу и её данные
  в общем межпользовательском кэше.

### Изменение существующего интерфейса
- В списке визиток заменить «Показать QR код»
  на «Показать визитку».
- Проверить варианты старой надписи:
  «Показать QR-код», подписи, title и aria-label.
- Новый пункт открывает презентационный экран.
- Существующее действие «Открыть визитку»
  продолжает вести на `/u/{slug}`.
- Не переименовывать «Скачать QR» и названия форматов
  там, где речь действительно идёт о скачивании QR.
- Не удалять QR-сервис и endpoints:
  они используются новым экраном.
- Старый отдельный QR-диалог больше не открывается
  из заменённого действия.
- Удалять устаревший UI-код только после проверки,
  что он не используется в других сценариях.

## T-014 — Прямое открытие контакта на Android без принудительного скачивания

### Статус
Done (код и автотесты); ручная матрица Android/iOS — см. ограничения в отчёте PR

### Цель
При нажатии «Сохранить контакт» передавать vCard на обработку
браузеру и операционной системе без принудительного скачивания
со стороны frontend.

На поддерживаемых Android-устройствах пользователь должен переходить
к системному открытию или импорту контакта без ручного поиска файла.

Сохранить существующее рабочее поведение на iOS.

### Контекст
Сейчас:
- На iOS после нажатия открывается системная карточка контакта.
- На Android файл скачивается, после чего пользователю
  приходится искать и открывать его самостоятельно.

В предыдущей реализации могли использоваться:
- Content-Disposition: attachment;
- атрибут download;
- fetch → Blob → программный клик по ссылке скачивания.

Необходимо проверить фактическую реализацию и убрать
принудительное скачивание из основного действия.

### Ограничение платформы
Веб-приложение не может гарантировать запуск приложения «Контакты»
на всех Android-устройствах и во всех браузерах.

Различать:
- передачу vCard браузеру;
- открытие системного обработчика файла;
- фактическое сохранение контакта пользователем.

Ни получение файла, ни открытие системного обработчика
не подтверждают сохранение контакта в адресной книге.

### Предусловия
- Реализована T-006 — генерация vCard.
- Кнопка «Сохранить контакт» работает на публичной странице.
- Есть правила публикации и фильтрации публичных данных.
- Есть рабочий iOS-сценарий для регрессионной проверки.

### Scope
- Аудит текущего механизма получения vCard.
- Прямое открытие URL vCard из основного действия.
- Корректные HTTP-заголовки для режима открытия.
- Отдельное явное действие «Скачать .vcf» как fallback.
- Пояснение для пользователей Android, если файл скачался.
- Обработка ошибок без ложного сообщения об успехе.
- Сохранение действующих правил приватности.
- Автоматические тесты и ручная проверка на устройствах.

### Вне scope
- Гарантированное открытие «Контактов» на любом Android.
- Автоматическое сохранение без подтверждения пользователя.
- Нативное Android-приложение или WebView-обёртка.
- intent:// и привязка к конкретному пакету приложения контактов.
- Web Share API.
- Запрос доступа к адресной книге.
- Изменение формата и состава vCard.
- Синхронизация, обновление и удаление контактов на устройстве.
- Изменение QR и презентационного экрана.
- Новые события аналитики.

### Основной сценарий
1. Получатель открывает публичную визитку.
2. Нажимает «Сохранить контакт».
3. Браузер выполняет прямую навигацию на endpoint vCard.
4. Сервер возвращает файл в режиме inline.
5. Если браузер и система поддерживают передачу обработчику,
   открывается системный интерфейс открытия или импорта контакта.
6. Пользователь подтверждает добавление самостоятельно.

### Запасной сценарий
Если браузер скачивает файл вместо открытия:
- пользователь видит доступную на странице подсказку;
- может открыть файл из уведомления или списка загрузок;
- при необходимости использует отдельное действие «Скачать .vcf».

Подсказка:
«Если файл скачался, откройте его из загрузок браузера
и выберите добавление или импорт контакта».

Не утверждать, что приложение умеет автоматически определить,
открылся ли системный экран или файл был только скачан.

### Frontend
Основное действие «Сохранить контакт»:
- использует обычную ссылку на endpoint vCard;
- не содержит download;
- не использует fetch → Blob для принудительного скачивания;
- не использует программный клик по download-ссылке;
- не открывает пустую вкладку через window.open;
- не блокируется обработчиком preventDefault
  без необходимости;
- сохраняет существующий текст кнопки.

Fallback:
- отдельная менее акцентная ссылка «Скачать .vcf»;
- использует серверный режим attachment;
- доступна независимо от определения ОС;
- не требует выбора платформы пользователем.

Не дублировать основной запрос через автоматический fallback:
это может привести к двум скачиваниям.

### API
Переиспользовать существующий endpoint:

GET /api/v1/public/cards/{slug}/vcard

Режим по умолчанию — открытие:

Content-Type: text/vcard; charset=utf-8
Content-Disposition: inline; filename="contact-{slug}.vcf"
Cache-Control: no-store
X-Content-Type-Options: nosniff

Для явного скачивания:

GET /api/v1/public/cards/{slug}/vcard?download=1

Content-Type: text/vcard; charset=utf-8
Content-Disposition: attachment; filename="contact-{slug}.vcf"
Cache-Control: no-store
X-Content-Type-Options: nosniff

### Правила API
- Оба режима используют один сервис генерации vCard.
- Содержимое файла в обоих режимах одинаковое.
- Параметр download валидируется.
- При отсутствии параметра используется inline.
- Поддерживается только согласованный режим download=1.
- Произвольные значения Content-Disposition из запроса запрещены.
- Имя файла формируется из валидного slug.
- Proxy или frontend route handler не должны заменять
  Content-Type и Content-Disposition на другие значения.
- Сохранить существующее ограничение доступа:
  только published-карточка без признака удаления.
- Сохранить существующие JSON-ошибки и HTTP-статусы.
- Ошибочный ответ не должен получать имя файла .vcf
  и заголовки успешного файлового ответа.

### Приватность и актуальность
- Скрытый e-mail не экспортируется.
- E-mail аккаунта не подставляется вместо e-mail карточки.
- В файл не попадают приватные и служебные данные.
- После редактирования новый запрос содержит актуальные данные.
- После снятия с публикации оба режима возвращают 404.
- Файлы не кэшируются между запросами.

### Сообщения пользователю
Разрешено:
- «Сохранить контакт».
- «Скачать .vcf».
- Пояснение о подтверждении импорта на устройстве.
- Подсказка, что делать, если файл скачался.

Запрещено без фактического подтверждения:
- «Контакт сохранён».
- «Контакт добавлен в телефон».
- «Приложение Контакты открыто».

Не добавлять индикатор успешного импорта по таймеру,
событию blur, visibilitychange или завершению HTTP-запроса.

### Ошибки
- Сохранить корректные 404 и 5xx от endpoint.
- Не подменять серверную ошибку успешным файлом.
- Не показывать успех при сетевой ошибке.
- При прямой навигации допустимо существующее поведение
  отображения ошибки endpoint.
- Не вводить дополнительный fetch только ради показа spinner,
  если это разрушает прямую обработку файла браузером.

- Публичный rate limit: fail-open при недоступности Redis; auth остаётся fail-closed.
- Referrer-Policy на `/u/{slug}`: `no-referrer`.

### Цель
Уменьшить вероятность массового обнаружения публичных карточек,
затруднить автоматический перебор и сократить раскрытие
публичных ссылок через служебные системы.

Сохранить:
- открытие визитки без регистрации;
- существующие ссылки и напечатанные QR;
- работу QR, vCard и контактов;
- независимую проверку владельца в приватных API.

### Граница защиты
Опубликованная карточка доступна любому, кто получил её ссылку.

Случайный slug:
- затрудняет угадывание;
- не заменяет авторизацию;
- не предотвращает пересылку ссылки;
- не отзывает ранее скачанные файлы и контакты.

Не позиционировать публичную визитку как конфиденциальное хранилище.

Конкретные значения не считать утверждёнными до аудита.

Смена пароля:
- текущий пароль + новый + подтверждение;
- успех → все refresh отозваны; сессия перевыпускается по правилам API;
- ошибка текущего пароля → сообщение без лишнего раскрытия.

Удаление:
- отдельная секция (не путать с Save);
- экран последствий (аккаунт недоступен; визитки и публичные ссылки закрываются; файлы удаляются best-effort; скачанные vCard/QR/скриншоты не отзываются; данные могут остаться в бэкапах БД ограниченное время);
- поле ввода `Удалить`;
- кнопка подтверждения активна только при точном совпадении;
- Enter в другом поле формы не должен случайно подтвердить удаление;
- состояние выполнения; ошибка не показывает ложный успех;
- успех → logout cookies clear → `/login`.

### Backend (план интеграции, не реализуется на Stage 2)
- `GET /api/v1/auth/me` — расширить флагом `hasPassword` (или `authMethods`).
- `PATCH /api/v1/auth/me` — `{ displayName }` only.
- `POST /api/v1/auth/password` — `{ currentPassword, newPassword }` → revokeAll refresh → issueSession.
- `POST /api/v1/auth/account/delete` — `{ confirmation: "Удалить" }` → collect storageKeys → delete User (cascade) → best-effort unlink files → clear cookies.
- AuthGuard / `me`: если User отсутствует → 401 (закрыть окно живого access JWT).
- Rate limit на password change и delete.
- Ownership только из сессии.

### Удаление данных
1. Закрыть доступ (удаление User + revoke tokens + clear cookies).
2. Cascade: Identity, RefreshToken, Card, links, events, photo rows.
3. Best-effort удаление файлов `storageKey`; идемпотентный retry при сбое FS.
4. Не обещать мгновенную очистку Postgres backups.
5. Публичные `/u/{slug}`, JSON, QR, vCard, media → 404 после удаления строк.

### Acceptance criteria (черновик)
- Пользователь видит только свой аккаунт.
- Меняется только согласованное имя; визитки не меняются неявно.
- Save / Cancel для имени; draft не теряется на ошибке.
- Password change только при hasPassword; VK-only UI без блока пароля.
- Delete требует точный ввод «Удалить»; отмена ничего не удаляет.
- После delete все сессии/access недействительны; публичка закрыта.
- Повторный delete / параллельный запрос идемпотентны или безопасны.
- Повторная регистрация/VK не возвращает старые карточки.
- Регрессии: login, edit-v2, T-016 security.

Изолированный UI на моках, без реальных мутаций API.
Маршрут: `/prototypes/account`.
Сценарии: просмотр, dirty имя, save/error, password (password user), скрытый password (VK), удаление, подтверждение, progress, error, результат.

T-019
## Фото в vCard при «Сохранить контакт»

### Статус
Stage 3 — задеплоено на prod (`main` @ `cb54164`); остаётся ручная проверка аватара на iOS/Android.

### Цель
При скачивании/открытии vCard с публичной визитки вместе с текстовыми
полями передавать и фото владельца (если оно есть у published-карточки),
чтобы контакт на iOS/Android сохранялся с аватаром.

### Предусловия
- T-006 — vCard 3.0 endpoint и кнопка «Сохранить контакт» работают.
- T-012 / T-015 — фото карточки хранится и отдаётся на публичке.
- T-014 — inline disposition на Android учтён (не ломать).

### Связь с T-006
В T-006 фото в vCard было **вне scope**. T-019 снимает этот запрет
только для поля фото карточки; остальные исключения T-006 сохраняются
(мессенджеры/CardLink в vCard не добавляем).

### Текущее состояние
- `VcardService` / `buildVCard30` сериализуют FN/N/ORG/TITLE/TEL/EMAIL/URL/NOTE.
- `VCardSource` **не** содержит photo.
- Фото живёт как `Card.photoUrl` + файл `storageKey` (webp) на диске / media URL.

### Согласованные решения
| Тема | Решение |
|---|---|
| Номер | T-019 |
| Когда включать PHOTO | Только если у published-карточки есть фото |
| Нет фото | Свойство PHOTO **не** добавлять; vCard как сейчас |
| Формат вложения | **Inline** base64 в vCard 3.0 (`PHOTO;ENCODING=b;TYPE=JPEG:…`), не URI |
| Почему не URI | Импорт в Contacts на iOS/Android часто игнорирует remote PHOTO |
| Исходник | Файл с диска по `storageKey` / photo storage (не скачивать через публичный HTTP сам у себя) |
| Кодировка картинки | Конвертировать stored webp → **JPEG** для TYPE=JPEG (совместимость) |
| Размер | Перед встройкой уменьшить до контакто-дружественного квадрата (ориентир ≤512px по стороне) и разумного веса (ориентир ≤100–150 KB JPEG), без порчи UX импорта |
| Ошибка чтения фото | vCard **без** PHOTO всё равно отдаём (не 5xx из‑за битого файла); залогировать без PII |
| UI | Текст кнопки можно не менять; поведение «сохранить контакт» обогащается аватаром |
| Аналитика | Событие `vcard_download` без изменений схемы |

### Scope
- Расширить `VCardSource` + `buildVCard30` свойством PHOTO (optional).
- В `VcardService.generate`: при наличии фото прочитать файл, resize/convert, передать bytes/base64 в serializer.
- Unit-тесты сериализатора (с PHOTO / без / folding длинной линии).
- Integration/e2e: карточка с фото → `/api/v1/public/cards/:slug/vcard` (или актуальный путь) содержит `PHOTO;ENCODING=b`.
- Ручная проверка импорта на iOS и Android (аватар в контакте).

### Вне scope
- PHOTO;VALUE=URI на CDN/media URL как основной вариант.
- Несколько фото / логотип компании / cover как PHOTO.
- Изменение модели БД.
- CardLink / мессенджеры в vCard.
- Синхронизация уже сохранённых контактов на устройстве.
- Отдельный UI «включить фото в vCard» (всегда on, если фото есть).

### Технический план (черновик)
1. `vcard.serializer.ts`: optional `photoJpegBase64` → линия `PHOTO;ENCODING=b;TYPE=JPEG:` + fold по октетам.
2. `vcard.service.ts`: resolve storage path from card photo; sharp (уже в photo pipeline) → jpeg buffer → base64; cap size.
3. Не логировать base64 / не класть photo URL с токенами в логи.
4. Сохранить Content-Type / Content-Disposition (T-014) без регрессий.
5. Документировать в `docs/api` / acceptance T-006 дополнение.

- [x] Published карточка **без** фото: vCard без PHOTO, остальное без регрессий.
- [x] Скрытый email по-прежнему не попадает в vCard.

- [ ] iOS и Android: после «Сохранить контакт» аватар виден в карточке контакта (ручной чеклист).
- [x] Регрессии: T-014 disposition, аналитика `vcard_download`, публичная страница.

T-020
## Вход через Яндекс ID

### Статус

### Предусловия

### Согласованные решения
| Тема | Решение |
|---|---|
| Номер | T-020 |

| Протокол | OAuth 2.0 Authorization Code (Яндекс ID / oauth.yandex.ru) |

| Успех | `302` → `/dashboard` |
| Ошибка | `302` → `/login?error=...` (коды в духе VK: `OAUTH_*`, `OAUTH_NOT_CONFIGURED`) |
